# Claude Code adapter

This is the harness map, not the system. The three levels and the revision
policy belong to [integration](../../docs/integration.md); roles and
delegation, to the [radiant-delegation skill](../../skills/radiant-delegation/SKILL.md).

## Agent entry

1. Resolve the root given by the global bootstrap and the consumer root.
2. Read the local `.radiant.json` and run
   `python3 <radiant-root>/validators/check_project.py <project-root>`.
   Follow the result before loading shared instructions. Without
   `.radiant.json`, the project is not a consumer yet: if the human asks for
   adoption, follow [Adopt in a project](../../docs/integration.md#adopt-in-a-project);
   if they do not, do not treat the project as a consumer.
3. With the gate satisfied, read that revision's
   [Constitution](../../constitution/CONSTITUTION.md), the
   [Engineering Baseline](../../engineering/engineering-baseline.md), the
   [capability index](../../docs/capabilities.md) and the applicable skill.
4. When coordinating roles, the main session is the orchestrator: read the
   delegation skill and use the `radiant-*` subagents described below.

In Radiant itself, [CLAUDE.md](../../CLAUDE.md) imports
[AGENTS.md](../../AGENTS.md). Radiant skills are read by path; no install in a
native catalog is needed.

## Set up the user

Requirements: Python 3.9+, Git and a checkout the harness can reach. At the
Radiant root:

```sh
python3 adapters/render_bootstrap.py
```

The command prints the [global block](../global.template.md) with the absolute
path of this checkout. To create an inspectable local file, ignored by Git:

```sh
python3 adapters/render_bootstrap.py --output .local/global.md
```

Include the block once in `~/.claude/CLAUDE.md`, keeping the existing
instructions. The block is the same for every harness: if `~/.claude/CLAUDE.md`
and another harness's global instructions point to the same file (for example
through dotfiles), a single block serves both. If the file is generated by Nix
or dotfiles, change its source. The generator refuses to overwrite files and
symlinks and does not change global configuration on its own.

## Capabilities

The capability → full model ID mapping is in
[capabilities.json](capabilities.json). It is this adapter's only source;
changing models means editing that file, verifying and regenerating the
subagents. Aliases are not used, so the evidence identifies the effective
model.

## Subagents

The profiles in [agents.json](../../skills/radiant-delegation/agents.json)
become user subagents:

```sh
python3 adapters/render_bootstrap.py --adapter claude-code --agents-dir ~/.claude/agents
```

Each file holds only frontmatter and a pointer to the role's section in the
delegation skill, with the absolute path of this checkout. The generator
refuses the whole run if any `radiant-*.md` already exists; to regenerate,
remove the six files and run it again.

- `disallowedTools: Agent` enforces the rule that delegated roles do not
  delegate.
- Profiles with `access: read` get `tools: Read, Grep, Glob, WebFetch,
  WebSearch`, with no writing and no shell. `write` profiles inherit the
  session's tools and permissions; the contract's boundaries hold through the
  "Access and boundaries" section of the delegation skill.
- Capability override through the contract: the role runs in the
  orchestrator's session, according to rule 5 of the skill. The invocation's
  `model` parameter only accepts family aliases and is not used, to preserve
  identification of the effective model.
- The main session must run on the `deep` model.

Subagent behavior according to the
[official documentation](https://code.claude.com/docs/en/sub-agents),
consulted on 2026-10-09.

## Usage measurement

This adapter's usage metric, per delegated round, is the `subagent_tokens` the
harness reports at the end of the round, plus the duration in seconds. It
measures context, not billed cost: when a round resumes the previous round's
context, the number includes the inherited context. The main session has no
per-round number; record its approximate context when closing the report.

## Maintenance

Run the [maintenance skill](../../skills/radiant-maintenance/SKILL.md)
locally, manually or through a scheduled task on the machine itself, with the
main session in `standard`. Cloud routines are out of scope: the report cannot
be persisted without an external write.

To schedule, pin the `standard` model from
[capabilities.json](capabilities.json) in the scheduler itself:

- Local task in the desktop app, under Routines: choose that model in the
  task's model picker. The model is not stored in the task's `SKILL.md`, and a
  task created by a scheduling tool from a session gets no model; check the
  picker in the edit form before the first run.
- System scheduler (cron, launchd): call the CLI in non-interactive mode with
  `--model` set to that ID.

Picker according to the
[official documentation](https://code.claude.com/docs/en/desktop-scheduled-tasks),
consulted on 2026-10-13; flags checked with `claude --help` in Claude Code
2.1.286, on the same date.

## Optional external procedures

When installed, they can serve as the "how to" of a role. Output always goes
to the paths in `.radiant.json`, never to the external skill's default paths.
Without them, the role follows Radiant only.

| Role | Suggested procedure |
| --- | --- |
| Ideation | `grilling` for Challenge |
| Design | `design-superpowers:design`, `design-superpowers:design-review` |
| Dev | `superpowers:test-driven-development`, `superpowers:systematic-debugging` |
| Verifier | `code-review`, `superpowers:verification-before-completion` |

## Set up the consumer

Follow [Adopt in a project](../../docs/integration.md#adopt-in-a-project). In
this harness, the instructions file is `CLAUDE.md` with the single line
`@AGENTS.md`.

## Undo

Remove only the `radiant:begin/end` block from `~/.claude/CLAUDE.md` and the
six `radiant-*.md` files from `~/.claude/agents/`. No Core file changes.
